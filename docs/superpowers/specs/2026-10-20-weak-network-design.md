# Лёгкий режим для слабого интернета (EDGE) — дизайн

Дата: 2026-10-20. Обсуждено с владельцем в чате; включение — автоматическое
(«сама»). Ориентир — IMO, который работает там, где Telegram уже не грузится.

## Зачем

Владелец был в зоне «E»: Telegram не грузился, а в cubechat сообщение висело с
«N повідомлення чекають на зв’язок». Цель — **там, где Telegram сдаётся,
сообщения и файлы cubechat всё равно уходят**. «Чем больше смс или файлов
смогут отправляться, тем лучше».

## Что нашли в коде (причины)

1. **Терпение рассчитано на хороший интернет.**
   `WebSocketNostrRelayClient.defaultPublishAckTimeout` = 2 с,
   `defaultProbeTimeout` = 2 с, `_reopenWait` = 3 с,
   `_ensureRelayAwakeForSend` ждёт 1,5 с. На EDGE круг «туда-обратно» 0,5–1 с
   плюс очередь в узком канале. Тишина 2 с → probe 2 с → сокет признан мёртвым
   → `_onDown` + `_reopenNow` → новый TLS+WebSocket (несколько секунд на EDGE)
   → снова тишина. Порочный круг: медленное соединение рвётся как мёртвое.
2. **~9 сокетов сразу**: conversation (3 публичных + `relay.cubechat.tech`),
   media (3), location (2). Каждый TLS-хендшейк — 5–8 КБ (сертификаты), все
   делят канал в десятки кбит/с.
3. **Служебный трафик на том же канале**: presence каждые 25 с
   (`presenceHeartbeat`) каждому активному контакту на все conversation-relay,
   маячки карты (location lane), отметки о прочтении, `_announceOverNostrTo`.
4. **Сам текст лёгкий**: кадр ~200–300 Б → base64 + JSON-событие с id, pubkey,
   sig, тегом `p` ≈ 750 Б, умножить на 4 relay ≈ 3 КБ.

Медиа: на сотовой сети медиа-подписка уже ставится на паузу
(`setMediaSubscriptions`), есть «эконом»-качество фото (до 96 КБ, 800 px,
`media_quality_controller.dart`) и отложенная до Wi-Fi загрузка
(`customizeDeferMedia`). Кусок для relay — 63 КиБ (`kRelayMediaChunkData`).

## Цели

- Короткий текст на EDGE уходит и получает галочку «доставлено через интернет».
- Файлы (фото, голосовые, документы) тоже уходят на EDGE — медленнее, но
  доходят, и после обрыва не начинаются заново.
- Режим включается и выключается **сам**, без кнопки.
- На хорошей сети поведение не хуже сегодняшнего.

## Не цели

- Менять формат кадра или Nostr-события (старые версии должны понимать новые).
- SMS через оператора. «Смс» у владельца — это сообщения cubechat.
- Свой бинарный протокол вместо WebSocket/Nostr.

## Анти-цели (провал, даже если «работает»)

- Сообщение показано доставленным, а оно не ушло.
- На хорошей сети стало медленнее или горячее.
- Сеть «дёргается»: режим включается/выключается каждые несколько секунд.

## Как работает

### 1. Определение «медленной сети» — само, по замерам

Источник истины — **наши собственные замеры**, а не тип сети от ОС (на Android
точный тип требует `READ_PHONE_STATE`, `connectivity_plus` даёт только
mobile/wifi). Замеряем:
- время от `EVENT` до `OK` по каждому relay (скользящее среднее/перцентиль);
- время от `connect` до `ready` у сокета;
- время ответа на probe.

Медленно — когда типичный ответ дольше порога (порог — решение исполнителя,
ориентир: медиана `OK` > 1,5 с или подключение > 5 с). Выход из режима — с
гистерезисом (несколько быстрых ответов подряд, не одна удача), чтобы режим не
мигал. Подсказки ОС (Android `NetworkCapabilities.getLinkDownstreamBandwidthKbps`,
iOS `CTTelephonyNetworkInfo` = Edge/GPRS) — по желанию исполнителя как ранний
сигнал, без новых разрешений.

Состояние живёт в одном месте (контроллер «качество связи»), им пользуются
relay-пул, `MessagingService` и UI.

### 2. Терпение по замерам, медленное ≠ мёртвое

- Таймаут ожидания `OK` = функция от замеренного времени ответа (например,
  ×3–4), не меньше нынешних 2 с, не больше ~15 с.
- Probe-таймаут и `_ensureRelayAwakeForSend` — так же.
- **Сокет, с которого за время ожидания пришёл хоть один байт, не считается
  мёртвым и не переоткрывается.** Переоткрытие — только при настоящей тишине.
- Повторная отправка того же события в тот же живой сокет вместо переоткрытия.

Константы с комментариями-замерами в `websocket_relay_client.dart` не удалять:
новые значения получают свой комментарий, почему.

### 3. Меньше сокетов на медленной сети

В режиме: держать открытыми **два** conversation-сокета — наш
`relay.cubechat.tech` и один лучший публичный по замерам. Остальные
conversation, media и location сокеты не открывать (или закрыть) до выхода из
режима. Публикация в «закрытую» полосу уходит в открытые сокеты — это уже
делает fallback в `publish()` («the lane's relays, if any are up; otherwise
the whole pool»).

Подписка: отправка только в два сокета безопасна, потому что среди них
`RelaySettings.meetingPointUrl` — «the one relay every build with lanes listens
on, whatever its settings» (`relay_settings_controller.dart`, добавляется в
conversation-полосу безусловно в `messaging_service.dart` ~стр. 987). Если наш
relay недоступен, режим держит два лучших публичных.

### 4. Очередь с приоритетами

Порядок на медленной сети: текст и сигналы звонка → отметки о прочтении →
presence → карта → медиа. Пока есть неотправленный текст, остальное ждёт.
- presence на медленной сети — реже (ориентир: раз в 2–3 минуты вместо 25 с);
  presence-TTL у собеседника это переживёт хуже — исполнитель решает, приемлемо
  ли «в сети» мигать, или слать presence только открытому сейчас чату.
- маячки карты — пропускать раунды, пока режим включён.
- отметки о прочтении — копить и слать пачкой.

### 5. Файлы

- В режиме фото автоматически идут в «эконом», если пользователь не выбрал
  явно «оригинал» для этого фото.
- Медиа идёт только в наш `/media` (он уже первичный), без параллельных копий.
- Кусок на медленной сети меньше 63 КиБ, чтобы один кусок успевал получить `OK`
  в разумное время. **Сначала проверить**, принимает ли приёмник кусок любого
  размера (манифест несёт число кусков; размер в манифесте?) — если меньший
  кусок ломает старые сборки, кусок не трогаем.
- Докачка: повторяется только неподтверждённый кусок, а не файл целиком.
  **Сначала проверить**, что уже делает `_drainFileQueue` и отправка кусков, —
  часть может уже быть (см. память «Already built — don't re-propose»).
- Файлы всегда в очереди после текста.

### 6. Что видит человек

Вместо вечного «чекають на зв’язок» в режиме — честная плашка над чатом/в
листе очереди: «Повільна мережа — надсилаємо» (uk/en через `flutter gen-l10n`).
Вид — по `glass-ui`, существующие стили плашек (без постоянной поверхности
заголовка — владелец это отвергал).

### 7. Логи

Одна строка в DebugLog при входе/выходе из режима с замерами
(`[NET] slow: ok-median 2.4 s, connect 7.1 s → 2 sockets`). Буфер лога 200
строк — не засорять построчно на каждое событие.

## Проверка

- Тесты с фейковым медленным сокетом (инъекция `connect` уже есть в
  `WebSocketNostrRelayClient`): ответ `OK` через 4 с → сообщение принято, сокет
  не переоткрыт; режим входит/выходит с гистерезисом; на медленной сети
  открыто 2 сокета; текст обгоняет presence и медиа.
- Существующие тесты relay-пула зелёные.
- Реальная проверка — только владельцем на телефоне в зоне «E» (у нас нет
  устройства). Дать ему точные шаги на русском: что сделать и какую строку лога
  прислать.
